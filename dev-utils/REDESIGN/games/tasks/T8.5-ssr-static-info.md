# T8.5 — SSR the static game info into the game page

Part of the game-page redesign (see `../requirements.md`). The game-meta panel and the
player username containers are **static** for a game's whole lifetime (live or dead). Render
them **server-side at request time** so they appear on first paint, instead of waiting a full
round-trip for the `gamestate` socket message (live) or `GET /api/game/:id` fetch (dead).

## Already landed (server side)

The server half is done; only the template render + the live-wire `youAreColor` migration remain.

- **`StaticGameState`** ([types.ts](../../../../src/shared/types.ts)) — the role-agnostic base both
  `FullGameState` and `DeadGameState` extend (was `GameStateBase`).
- **`buildStaticGameState`** ([gameutility.ts](../../../../src/server/game/gamemanager/gameutility.ts))
  factored out of `produceFullGameState`; **`produceDeadStaticGameState`** + the shared
  `assembleStaticGameState` mapper ([deadgamestate.ts](../../../../src/server/game/gamemanager/deadgamestate.ts))
  fetch only the static columns (no `icn`); **`produceStaticGameState(id)`**
  ([gamemanager.ts](../../../../src/server/game/gamemanager/gamemanager.ts)) dispatches live/dead and
  returns `{ isLive, state }` (or `undefined` → 404).
- **Role resolution** is computed once server-side in **`getGamePageState`**
  ([gamePageController.ts](../../../../src/server/controllers/gamePageController.ts)): live matches
  members AND guests via `memberInfoEqPartial`
  ([memberInfoUtil.ts](../../../../src/server/utility/memberInfoUtil.ts)); dead matches members only
  via `resolveDeadParticipantColor`.
- **Route** ([root.ts](../../../../src/server/routes/root.ts)) delegates `/game/:id` to
  `getGamePageState`, which builds the display-ready **view-model** (`meta`) and the
  `gamePageData` channel `{ id, isLive, youAreColor? }`, and 404s on a malformed/nonexistent id
  (this replaced the old `isGameIdTaken` check). `getSimplifiedGameString` now includes the base62
  id for URL lookup.

The view-model `meta` passed to the template:
`{ variant: { iconId, name }, speed: { iconId, category }, timeControl, rated, timeCreated, isTimed,
players: PlayerGroup<{ name, elo? }> }`. **Open follow-ups flagged during review:** variant name is
English (`getVariantName`) though the page is otherwise localized; custom games fall back to
`{ iconId: 'svg-pawn', name: 'Custom' }`.

  material, moves, actions, disconnect, chat) as their static skeleton / `.hidden` — untouched.

### 3.5. Drop `youAreColor` from the live wire; client reads it from `gamePageData` (the "E" chunk)

The wider-blast-radius change (touches the live socket protocol — land as its own commit). Role now
lives in `gamePageData` (resolved server-side, works for guests whose `httpOnly` `browser-id` can't
be read client-side), so it must come off the wire:
- **Schema** ([types.ts](../../../../src/shared/types.ts)): remove `youAreColor` from
  `SubscribedGameStateSchema`, leaving it `FullGameStateSchema` + optional `participantState`.
- **Server overlay builder** (`gameutility.ts` `sendParticipantGameState`, ~L403): stop attaching
  `youAreColor`; keep attaching `participantState` for participants.
- **Client `GameSchema`** (`socketschemas.ts`): mirror the schema change for the incoming
  `gamestate` action (coordinate with T9's "B" chunk so they agree).
- **Client role source:** the loader signature stays `loadGameFromState(state, youAreColor?)`, but
  the entry now passes `window.gamePageData.youAreColor` (live, dead, spectator) instead of
  `state.youAreColor`. The client infers participant-ness from `youAreColor !== undefined`.

### 4. Ownership boundary with T9's render handlers

The SSR'd regions (game-meta info, participant list, player-bar name/rating) are now **owned by
SSR**. T9's side-bar render handlers (the "D" chunk) must populate only the dynamic regions and
**must not** re-render them; **role comes from `gamePageData`**, not the wire or a username match.
The live clock *values* and the eloChange deltas still come from the client (they write into the
SSR'd bars' `.clock` / a new `.eloChange`, not by rebuilding the bar). Leave a comment in the
template marking SSR-owned regions so the passes don't collide.

## Out of scope / deferred

- Slimming the wire game **data** (e.g. dropping the now-SSR'd `rated`/`players`) — owned by
  **T13**, gated on the new page being canonical + an audit that no client logic consumes them. Only
  the per-viewer `youAreColor` role tag migrates off the wire here (§3.5); the game data stays.
- The confident-rating-for-dead-games DB fix (separate task) — until it lands, SSR'd dead ratings
  display as confident, same as the JSON does today.
- gamerule-mods, material, moves, chat, all dynamic deltas — client (T9+).

## Constraints

- Don't have the client read game **data** from the DOM — the loader's source of truth stays the
  typed wire message. (`youAreColor` from the `gamePageData` global is the one deliberate exception.)
- No double-render: each static region rendered exactly once (SSR), each dynamic region once
  (client). Mark the boundary clearly.
- Follow `CLAUDE.md`: reference source types; tight jsdoc; tabs. Run `npm run type-check --silent`
  + `npm run lint --silent`.

## Acceptance (remaining)

- Loading `/game/:id` for a **live** game returns HTML whose side bar already shows the variant /
  speed / time control / mode, both players' names + ratings (bars oriented to the viewer), and
  `XX:XX` clocks — before any socket message; an **untimed** game shows no clock placeholders.
- The same for a **dead** game (id in the DB), with no socket/HTTP state yet.
- A spectator (non-participant) sees white-POV orientation; a **guest participant** of a live game
  gets their correct color (server-resolved from the `browser-id` cookie) in both the SSR bar
  orientation and `gamePageData.youAreColor`.
- The live `gamestate` socket message **no longer carries `youAreColor`**; the client reads role
  solely from `gamePageData`. `participantState` still arrives on the wire for participants.
- When the full state subsequently arrives, the client fills only the dynamic regions and does
  **not** flicker/rebuild the SSR'd static content.
