# T8.5 — SSR the static game info into the game page

Part of the game-page redesign (see `../requirements.md`). The game-meta panel and the
player username containers are **static** for a game's whole lifetime (live or dead) — they
never change once the game exists. Render them **server-side at request time** so they appear
on first paint, instead of waiting a full round-trip for the `gamestate` socket message (live)
or the `GET /api/game/:id` fetch (dead) to populate an empty side bar.

Depends on T8 (the game.njk markup + class names) and on the existing state builders
(`produceFullGameState`, `produceDeadGameState`) — both already assemble the shared
`GameStateBase`. Independent of T9–T12; **should land before T9's side-bar render handlers**
so ownership of the static regions is settled (see §4).

## Core principle — SSR the static display; resolve role once, server-side

The over-the-wire game **data** is not slimmed: the client loader keeps consuming the typed
fields (`variant`, `timeControl`, `timeCreated`, `gameConclusion`) from the wire — never from
the DOM. SSR is a **pure first-paint render** of the *display* of the static fields; the data
still arrives typed for the loader. Clean split, **no region rendered twice**:

- **SSR renders (server, once, never re-touched):** game-meta info row (variant, speed, time
  control, mode), the start time, the white/black participant list, and the two board-POV
  player bars (name + rating + `XX:XX` clock placeholder).
- **Client renders on full-state arrival (T9 handlers):** everything dynamic or un-SSR-able —
  gamerule-modifications row, material bars, moves table, live clock values, draw-offer /
  disconnect / result blocks, rating-change deltas, spectator count, chat.

The client render handlers **must not** overwrite the SSR'd static DOM (§4).

### `youAreColor` migrates from the wire to an SSR-injected global

This task also makes the live and dead role-resolution **symmetric** by resolving the viewer's
color **once, server-side, at SSR** (§2) and injecting it into `window.gamePageData` — then
**dropping `youAreColor` from the live socket overlay**. Rationale: a guest's only identity is the
`httpOnly` `browser-id` cookie, which client JS cannot read, and a guest's `browser_id` must not
be broadcast to spectators — so a guest *cannot* compute its own color client-side. Only the
server can (it has the cookie + the game's `playerData`), and the SSR route already does for bar
orientation. Reusing that one computation for game logic too removes the live overlay's
`youAreColor` and the dead path's username-matching entirely. `youAreColor` is **static** (never
changes), so a JS global is safe; this is a typed role tag, *not* DOM-scraping, so it doesn't
violate "the wire is the loader's source of truth."

Kept on the live wire: **`participantState`** (draw offer / disconnect — genuinely dynamic,
per-subscriber). The client infers participant-ness from `gamePageData.youAreColor !== undefined`.

> **Blast radius:** unlike the rest of this task (purely additive), this touches the **live socket
> protocol** — `SubscribedGameStateSchema`, the server overlay builder, and the client `GameSchema`.
> Land it as its own commit (see §3.5). T9/T10/T11 are written assuming role comes from
> `gamePageData`, not the wire.

## What is static (SSR-able) vs. not

All static display is derivable from the shared `GameStateBase` fields ([types.ts](../../../../src/shared/types.ts) `GameStateBaseSchema`) via **shared** utils (importable server-side):

| Display | Source |
|---|---|
| Variant name | `variantregistry.getVariantName(variant)` |
| Variant group icon id | `variantregistry.getVariantGroupIconId(variantregistry.getVariantGroup(variant))` |
| Time control text | `timeControl` |
| Speed icon id + label | `clockutil.getSpeedIconId(timeControl)` / `getSpeedCategory` |
| Mode | `rated ? 'Rated' : 'Casual'` |
| Start time | `timeCreated` (emit the epoch ms; client formats the relative string — it ticks) |
| Player name + rating | `players[color]` (`metadatautil.getFormattedElo` for the elo) |
| Timed? (clock placeholders) | `timeControl !== '-'` |

**Not SSR'd** (deferred to the client full-state pass): gamerule-modifications row
(needs `GameRules` — for custom positions only derivable by parsing the ICN, which the server
must not do), material, moves, result banner, spectator count, eloChange deltas.

**Custom-variant note:** `variant` is currently a strict preset enum, so the table above assumes
a preset code. A separate, prerequisite decision reshapes `variant` into a preset-vs-custom
discriminated union. **Coordinate with that decision** — if it has landed, branch the variant
name/icon derivation on `variant.kind` and leave the custom arm's name/icon to a sensible
fallback; if it has not, this task targets preset variants only.

## Required changes

### 1. Server — a unified static-base producer

Add a function that returns the typed `GameStateBase` for an id **regardless of liveness**, plus
the liveness flag: e.g. `produceGameStateBase(id): { isLive: boolean; base: GameStateBase } | undefined`
(`undefined` → game doesn't exist → 404). It dispatches:
- **Live** (`getGameByID(id)` hit): build from the `activeGames` entry. **Factor the base
  assembly out of `produceFullGameState`** ([gameutility.ts:445](../../../../src/server/game/gamemanager/gameutility.ts#L445)) so the
  field-mapping isn't duplicated — `produceFullGameState` then spreads the extracted base and
  adds `moves`/`clockValues`.
- **Dead** (DB row exists): reuse `produceDeadGameState` ([deadgamestate.ts](../../../../src/server/game/gamemanager/deadgamestate.ts)) and take its base
  fields (the `icn`/`ratingChanges`/`finalClocks` extras are unused here), or factor its base
  assembly out the same way. Do **not** duplicate the column→field mapping.

Because `GameStateBase` is identical across live and dead, the consumer (the route/template) is
liveness-agnostic for the static display.

### 2. Server — resolve `youAreColor` at SSR time (single source for display **and** logic)

The `/game/:id` route already runs `resolveAuth`, so `req.memberInfo` carries the viewer's
identity (`{signedIn:true, user_id, username}` or `{signedIn:false, browser_id}`). Compute
`youAreColor` by matching it against the participants — the same matching the live overlay does
today, just done once here, for both paths:
- **Live:** match `req.memberInfo` against each color's `match.playerData[color].identifier`
  (`AuthMemberInfo`: `user_id` for members, `browser_id` for guests — so guests resolve correctly).
- **Dead:** match `req.memberInfo.user_id` against the `player_games` rows' `user_id` (dead guests
  aren't identifiable → not a participant; acceptable, review is read-only).
- Not a participant (spectator, or unmatched) → `undefined` → white POV.

This single value serves **both** the SSR bar orientation (which player fills top vs. bottom) and
the client's game logic (participant gating, board POV) — see §3.5. It is **not** also sent on the
live wire.

### 3. Route + template — render the static regions

- **Route** ([root.ts:46](../../../../src/server/routes/root.ts#L46)): call `produceGameStateBase`; on `undefined` →
  `send404`. This also **closes the currently commented-out existence check** ([root.ts:52](../../../../src/server/routes/root.ts#L52),
  `// if (!isLive && !isGameIdTaken(decoded)) return send404`) — the producer returning `undefined`
  is the real nonexistent-game 404. Build a small **view-model** of display-ready fields (derive via
  the shared utils in the table above — precompute, since Nunjucks can't call them) plus
  `youAreColor` and `isTimed`, and pass it to `res.render('game.njk', …)`. Drop the now-resolved
  `isLive` recompute (reuse the producer's flag). **Extend `gamePageData`** to `{ id, isLive, youAreColor }` (`youAreColor`
  omitted/undefined for spectators) — this is the client's source for role (§3.5).
- **Template** ([game.njk](../../../../src/server/views/game.njk)): replace the `EXAMPLE` hard-coded content in the
  `.game-meta` info row, `.meta-players` list, and the two `.player-bar`s with the view-model:
  - meta-info: variant icon `<use href>` + name, speed icon + time control, mode text.
  - `.meta-started`: `<time>` with the epoch ms (client formats relative).
  - `.meta-players`: white row then black row (fixed order, no `youAreColor`).
  - `.player-bar top`/`bottom`: oriented by `youAreColor` (top = opponent / black for
    spectator; bottom = you / white). Render the `.clock` placeholder (`XX:XX`) **only when
    `isTimed`**; omit the clock span entirely for untimed games.
  - Keep the dynamic blocks (`.result-banner`, `.meta-rules`, `.meta-spectators`, `.eloChange`,
    material, moves, actions, disconnect, chat) as their static skeleton / `.hidden` — untouched
    by this task.

### 3.5. Drop `youAreColor` from the live wire; client reads it from `gamePageData`

This is the separate-commit, wider-blast-radius change (see Core principle):
- **Schema** ([types.ts:246](../../../../src/shared/types.ts#L246)): remove `youAreColor` from `SubscribedGameStateSchema`,
  leaving it `FullGameStateSchema` + optional `participantState`. (`SubscribedGameState` becomes
  "full state + the participant's dynamic overlay" — no role tag.)
- **Server overlay builder** (`gameutility.ts` / `subscribetogame.ts`, where the overlay is layered
  on at delivery — around [gameutility.ts:388](../../../../src/server/game/gamemanager/gameutility.ts#L388)): stop attaching `youAreColor`;
  keep attaching `participantState` for participants.
- **Client `GameSchema`** (`socketschemas.ts`): mirror the schema change for the incoming
  `gamestate` action (this is also what T9's "B" chunk wires — coordinate so they agree).
- **Client role source:** the entry/loader reads `window.gamePageData.youAreColor`. The loader
  signature stays `loadGameFromState(state, youAreColor?)`, but the entry now passes
  `gamePageData.youAreColor` (live, dead, and spectator) instead of `state.youAreColor`.

### 4. Ownership boundary with T9's render handlers

The static regions above are now **owned by SSR**. T9's side-bar render handlers (the "D" chunk)
must populate only the dynamic regions and **must not** re-render the SSR'd game-meta info,
participant list, or player-container name/rating. Likewise **role comes from `gamePageData`**, not
the wire or a username match — T9/T10/T11 are written to assume this. Update those task notes (or
leave a comment in the template marking SSR-owned regions) so the passes don't collide. The live
clock *values* and the eloChange deltas still come from the client (they write into the SSR'd
bars' `.clock` / a new `.eloChange`, not by rebuilding the bar).

## Out of scope / deferred

- Slimming the wire game **data** (e.g. dropping the now-SSR'd `rated`/`players`) — owned by
  **T13** (live socket-protocol reshape), gated on the new page being canonical + the
  custom-variant union being settled + an audit that no client logic consumes them. Low priority
  (a few hundred bytes vs. the large `moves` array). Only the per-viewer `youAreColor` role tag
  migrates off the wire here (§3.5); the game data stays.
- The custom-variant `variant`-union reshape (separate prerequisite decision).
- The confident-rating-for-dead-games DB fix (separate task) — until it lands, SSR'd dead ratings
  display as confident, same as the JSON does today.
- gamerule-mods, material, moves, chat, all dynamic deltas — client (T9+).

## Constraints

- Don't have the client read game **data** from the DOM — the loader's source of truth stays the
  typed wire message. (`youAreColor` moving to the `gamePageData` global is a typed role tag, the
  one deliberate exception; everything else stays additive.)
- No double-render: each static region is rendered exactly once (SSR), each dynamic region once
  (client). Mark the boundary clearly.
- Avoid redundancy: factor the `GameStateBase` assembly rather than copying field mappings out of
  the existing builders. Derive display via the existing shared utils — don't reimplement them.
- Follow `CLAUDE.md`: reference source types; tight jsdoc; tabs. Run `npm run type-check --silent`
  + `npm run lint --silent`.

## Acceptance

- `npm run type-check --silent` + `npm run lint --silent` pass.
- Loading `/game/:id` for a **live** game returns HTML whose side bar already shows the variant /
  speed / time control / mode, both players' names + ratings (bars oriented to the viewer), and
  `XX:XX` clocks — before any socket message; an **untimed** game shows no clock placeholders.
- The same for a **dead** game (id in the DB) over the SSR route, with no socket/HTTP state yet.
- A nonexistent id 404s. A spectator (non-participant) sees white-POV orientation.
- A **guest participant** loads `/game/:id` and gets their correct color (server-resolved from the
  `browser-id` cookie) — both in the SSR bar orientation and in `gamePageData.youAreColor`.
- The live `gamestate` socket message **no longer carries `youAreColor`**; the client reads role
  solely from `gamePageData`. `participantState` still arrives on the wire for participants.
- When the full state subsequently arrives, the client fills only the dynamic regions and does
  **not** flicker/rebuild the SSR'd static content.
